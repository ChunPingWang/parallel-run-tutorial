# ADR-003：副作用與資料隔離策略

- **狀態**：已接受
- **日期**：2026-07-25

## 背景

平行測試會讓新應用收到真實交易請求。若新應用共用正式資源，將造成**重複記帳、重複發送簡訊、重複呼叫收單清算**等不可逆後果。這是本 PoC 最高等級的風險。

## 決策

**採「應用層 dry-run + 資源層隔離 + 網路層阻斷」三層防護，且三層皆須實際驗證。**

| 層 | 措施 |
|---|---|
| 資料庫 | 新應用連影子 DB（正式庫還原副本或 CDC 單向同步）。**絕不共用正式庫** |
| 外部系統 | 收單、清算、核心主機、簡訊/Email 一律 WireMock/Hoverfly stub |
| MQ / Kafka | 發往 `shadow.` 前綴 topic，獨立 consumer group |
| 排程 / 批次 | PoC 期間全數關閉 |
| 應用層 | 收到 `X-Shadow-Request: true` 進 dry-run：跳過發送類動作、跳過冪等鍵檢查、log 標記 `shadow=1` |
| 網路層 | NetworkPolicy 阻斷 `shadow` namespace egress 至正式 DB 與外部端點 |

## 理由

**不能只靠應用自律。** 應用層開關會因設定錯誤、程式碼分支遺漏、環境變數未帶入而失效，且失效時毫無徵兆。網路層阻斷是最後一道防線，且能在錯誤發生時立即失敗（fail loudly）而非靜默寫入。

## 後果

**正面**
- 即使應用層 dry-run 判斷有誤，網路層仍能阻擋
- 失敗模式明確（連線被拒），易於偵測

**負面**
- 影子 DB 與 CDC 同步帶來額外基礎設施成本
- CDC 延遲會造成資料面假陽性（見 ADR-004 與 ADR-005 的容忍窗口設計）
- stub 回應與真實外部系統可能不同，部分行為無法在 PoC 驗證

## 驗證要求

檢核表 **T-14 為 Gate 阻擋項**：必須在新應用 Pod 內實際嘗試連線正式 DB 與外部端點，**確認不通**並留存輸出。

```bash
kubectl -n shadow exec deploy/new-app -- \
  timeout 3 bash -c '</dev/tcp/prod-db.bank.internal/1521' ; echo $?
# 回傳非 0 才算通過。若為 0 → 立即停止 PoC。
```
